## 失败处理

### Recovery Ladder

所有反射的失败统一遵循 4 级恢复：

| 级别 | 行动 | 执行者 |
|------|------|--------|
| L1 Resume | 同角色重试（附失败上下文） | root 自动 |
| L2 Re-spawn | 换同类型角色接手 | root 自动 |
| L3 Re-assign | 降级任务范围后重分配 | root 自动 |
| L4 Escalate | 上报 b1 | root 请示 |

> **关键区分**：审计/验证反射失败第 1 次 → L1 Resume（同角色重试）；实现反射失败第 1 次 → 直接 L2 Re-spawn（跳过 L1，换角色接手）。原因：实现失败通常是方案问题而非执行问题，同角色重试价值低。

### Circuit Breaker

每反射维护 CB 状态（`trigger-stats.json`）：CLOSED →(≥3连败)→ OPEN →(24h)→ HALF-OPEN →(≥2连胜)→ CLOSED。OPEN 时终端反射 skip，关键反射 L4。

并行 N 反射必须全部 accounted（SUCCESS 或 SKIP）后才进下一批，MISSING 触发 Recovery Ladder。

## 调研分级

| 级别 | 执行方式 |
|------|---------|
| L0 快速扫描 | yomi 单次快速退出 |
| L1 标准调研 | yomi 标准扫描 |
| L2 深度调研 | yomi 深度分析 |
| L3 竞争假设 | yomi×3 并行 + shin DA |

**L3 触发条件**：高影响 + ≥2 方案 + 无明显最优 + 成本合理。

**L3 输出格式** — yomi 报告：`核心论点 / 支持证据 / 风险反例 / 置信度(H/M/L) / 推荐度(H/M/L)`；shin DA 报告：`假设 X 最弱点 + 反证 / 隐性前提风险`。

## 常用路径

| 场景 | 路径 |
|------|------|
| bug 修复 | 调研 → 实现 → 审计 → 提交 |
| 新功能 | 调研 → 探索 → 实现+文档 → 审计 → 提交 |
| 配置变更 | 文档 → 提交 |
| 反馈规则化 | 记忆 → 吞食 → 文档 → 提交 |
| 角色创建 | root 决策 → 定义 → 文档 → 提交 |
| 论文修改 | 实现(编辑) → 审计(gate-loop) → 提交 → 实现(DOCX) |
| 高影响决策 | L3 竞争假设 → 实现+文档 → 审计 → 提交 |
| skill 创建 | 实现(创建) → 验证(触发测试) → 审计 → 提交 |

> 所有路径末尾：提交 → 日记 + 记忆（并行，终端反射，链路结束）

## 并行派发协议

### 何时使用并行派发

| 场景 | 并行反射 | 示例 |
|------|---------|------|
| Phase 3 实现+文档 | implement + document | tetsu 改代码，fumio 写文档 |
| 终端反射 | journal + memory | fumio 日记，yume 记忆 |
| L3 竞争假设 | research ×3 | yomi ×3 并行调研 |

### 标准流程

1. **派发前**：root 调用 start-batch 注册批次
```bash
python3 ~/.claude/hooks/post-agent-trigger-stats.py start-batch <batch_id> <reflex1,reflex2> [timeout_minutes]
# 示例：
python3 ~/.claude/hooks/post-agent-trigger-stats.py start-batch phase3-impl-doc implement,document 10
```

2. **派发**：root 使用 Agent tool 的 `run_in_background=true` 并行启动多个 agent

3. **自动追踪**：每个 agent 完成时，PostToolUse/Agent hook 自动调用 `update_batch_reflex()`

4. **完成判定**：所有反射状态 ≠ PENDING 时，批次自动归档到 `parallel_batches.history`

5. **超时处理**：超过 timeout_minutes 后，PENDING 反射自动标记为 MISSING，触发 Recovery Ladder

### 批次状态查询

```bash
python3 ~/.claude/hooks/post-agent-trigger-stats.py check-batch
```

### 约束
- 并行 N 反射必须全部 accounted（SUCCESS / FAILURE / SKIP）后才进下一批
- MISSING 触发 Recovery Ladder
- 批次历史最多保留 10 条

## 对抗性协议（Adversarial Protocol）

反射系统的审计和验证阶段内置对抗性，防止自我确认偏差。

### 红队审计（shin）

审计不是检查清单打勾，而是主动攻击：

| 攻击维度 | 方法 | 示例 |
|----------|------|------|
| 边界输入 | 构造极端/畸形输入测试实现 | 空字符串、超长输入、特殊字符 |
| 逻辑反驳 | 挑战实现方案的前提假设 | "如果并发调用会怎样？" |
| 回归风险 | 检查修复是否破坏已有功能 | "这个改动影响了哪些调用者？" |
| 遗漏检测 | 寻找实现中未覆盖的场景 | "文档更新了，但配置没同步" |

shin 审计输出必须包含 `## 攻击发现` 章节，即使无发现也要写"已尝试 X 个攻击向量，无发现"。

### 决策质疑（shin DA 模式）

root 做出决策后，shin 以 Devil's Advocate 身份质疑：

- **触发条件**：shin 判定为 L2 对抗等级的变更
- **质疑格式**：
  ```
  ## 决策质疑
  - 最弱假设：{root 方案中最脆弱的前提}
  - 替代方案：{至少一个不同路径}
  - 如果错了：{最坏情况和回滚成本}
  ```
- **root 必须回应质疑后才能推进实现**（可以否决但必须给理由）

### DA 约束

- **1 轮限制**：shin 质疑 → root 回应 → 结束。shin 可在审计结论中记录保留意见，但不再追加质疑轮次
- **禁止递归**：DA 模式下的审计输出直接走 通过/不通过 → 提交/Recovery，不再触发 DA
- **对抗等级由 shin 判定**：root 不得降级 shin 的对抗等级判定

### 验证对抗（haku）

haku 验证不是"跑一遍看通过"，而是试图让实现失败：

| 对抗方式 | 说明 |
|----------|------|
| 模糊输入 | 给 hook/脚本喂入畸形 JSON、缺字段、类型错误 |
| 竞态模拟 | 并发调用同一文件的读写场景 |
| 依赖断裂 | 假设某个依赖文件不存在或损坏 |
| 状态污染 | 在脏状态下运行（CB=OPEN、recovery pending 等） |

### 对抗性等级

| 等级 | 触发条件（shin 判定，非 root 自评） | 强度 |
|------|--------------------------------------|------|
| L0 轻量 | 单文件 + 非配置文件 + 无转移规则变更 | shin 标准审计 + haku 基础验证 |
| L1 标准 | 多文件 OR 配置文件变更（reflex-config/settings） | shin 红队 + haku 模糊输入 |
| L2 强对抗 | trigger-map/CLAUDE.md/registry 变更 OR 角色创建/销毁 OR 不可逆操作 | shin DA 质疑(1轮) + haku 全对抗 |

### 风险量化（Severity × Likelihood 矩阵）

L2 对抗中，shin 用 5×5 矩阵评估发现的问题：

| | 极低(1) | 低(2) | 中(3) | 高(4) | 极高(5) |
|--|---------|-------|-------|-------|---------|
| 极高(5) | 5 | 10 | 15 | 20 | 25 |
| 高(4) | 4 | 8 | 12 | 16 | 20 |
| 中(3) | 3 | 6 | 9 | 12 | 15 |
| 低(2) | 2 | 4 | 6 | 8 | 10 |
| 极低(1) | 1 | 2 | 3 | 4 | 5 |

行=影响严重度，列=发生可能性。

| 风险分 | 处理 |
|--------|------|
| ≥15 Showstopper | 必须修复后才能提交 |
| 10-14 High | 应修复，可降级处理 |
| 5-9 Monitor | 记录并监控 |
| <5 Accept | 接受风险 |

### 论证验证（Toulmin Model）

shin 的批评和 root 的回应都必须满足论证质量标准：

| 要素 | 说明 | 示例 |
|------|------|------|
| Claim | 明确的断言 | "这个修改会导致竞态条件" |
| Data | 支撑数据 | "两个 hook 并发写同一文件" |
| Warrant | 逻辑链接 | "无锁保护的并发写 = 数据丢失" |
| Rebuttal | 反驳考虑 | "但 fcntl.LOCK_EX 已处理" |

缺少 Data 或 Warrant 的批评视为无效（稻草人），root 可直接否决。

### L3 对抗技术选择

高影响决策触发 L3 竞争假设时，按场景选择对抗技术：

| 场景 | 技术 | 说明 |
|------|------|------|
| 产品/功能决策 | Council Debate | 多角色 2 轮辩论（并行） |
| 架构/安全决策 | Attack Trees | 系统枚举攻击向量 AND/OR 分解 |
| 战略/不可逆决策 | Pre-mortem | 假设失败，回溯原因 |
| 流程/政策变更 | Tabletop Exercise | 逐轮注入信息，测试决策链 |

## 验证铁律

1. 主会话独立验证，不信任子代理自报
2. 视觉变更需端到端确认
3. 同类失败 ≥ 2 次 → 换策略
